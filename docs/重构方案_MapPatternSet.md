# MapPatternSet 重构方案（v0 · 待人工确认）

> 2026-11-15 起草。**本文件只是方案，代码尚未改动。**
> 目标：支持「新建 / 修改 MapPatternSet」与「在 set 里增删 pattern」，`patternCount` 由 pattern 自动派生。

---

## 一、先给结论（全部实测过，不是推测）

1. **`patternId` = ⌊setId / 1000⌋ × 1000 + 组内前缀和**
   （组 = set id 的千位；moremap / base_sot 两份 bin，101/101 个 set 的 firstPid 全部对得上）
2. **组之间互不影响**：改 0 组某个 set 的 pattern 数，只会平移 0 组里它之后的 pid；1000 组一个都不动，反之亦然。
   > 这条是对我上一轮说法（"从 pid 160 起全体 +2"）的**更正**——实际只影响同组，爆炸半径小得多。
3. **空号空间**：0 组现在用到 `0..319`，`320..999` 共 680 个号是空的；1000 组用到 `1000..1200`，`1201..1999` 共 799 个号空着。
4. **新 set 一律放表尾**（id = max+1）→ 落在 1000 组 → 它的 pid 从 `1201` 起。
5. **`patternCount` 是派生值** = 该 set 里实际 pattern 的个数，**不给用户填**。
6. **除 `patternCount` 外，整行 440 字节所有字段：默认照抄官方对应 set，全部可手改**（高级字段折叠）。
7. **set 级池子是"直方图"**（`eventModifier*_Count`、`night1/2BossModifier*_Count`）：值 = 某个 modifier，计数 = 该 set 里用它的 pid 个数。
   证据：set 0 池子 `{444:10, 439:10}` 与其 pid 的 `bossModifier1` 分布逐项相等；事件池同理（`0×12 + 180×5 + 200×3 = 20 = patternCount`）。
   所以加/删 pattern 后要「一键重算」，默认仍先照抄官方。

### 2.3 三个身份

- **set 的身份**（夜王 / 地图类型）不在 set 行里，而在它**每条 flag 行**的 `targetBoss`（s32）/ `rareMap`（s16）上，同一 set 内完全一致。
- **pid 的归属**由 flag 行的 `patternSetId`（s16）+ 位置共同决定。
- 空 set（`patternCount=0`）**没有 flag 行**，所以它的夜王/地形只存在于工具侧模型 + 名字里 —— 等插入第一个 pattern 时才真正落到 flag 行。官方也有 32 个这种空壳 set，合法。

## 三、工具侧模型

```
Bin
 ├─ binPath, params{}
 └─ groups[]                      # 千位组：0 组 / 1000 组
     ├─ base = 0 | 1000           # pid 基址
     └─ sets[]                    # 按 set id 升序
         ├─ id                    # set 行 id
         ├─ name                  # set 行 _name
         ├─ fields{weight, chaosW, pools{...}, unknown{...}}
         ├─ boss, rareMap         # 来自 flag 行；空 set 时来自工具侧记录
         ├─ patterns[]            # 按 pid 升序
         │    ├─ pid
         │    ├─ flagRows[]       # 原始字段全保留（为将来逐行编辑）
         │    ├─ playArea         # 1 行
         │    └─ spots[]          # 原始行
         └─ patternCount          # = len(patterns)，只读派生
```

派生链路：`pid(set, i) = group.base + Σ(patternCount of 同组更小 id 的 set) + i`

## 五、重编号引擎（核心）

```
输入：某个 set 的 pattern 列表变化（插入/删除/删 set）
1) 只算受影响的组（该 set 所在千位组）
2) 组内按 set id 升序重算：pid = base + Σ counts（从小到大）
3) 生成 oldPid → newPid 映射（只含变化项）
4) 三张表按映射改 patternId（flag / playarea / spots）
   异常：插入/删除导致 pid 冲突、set 不存在、flag 行缺失
5) 只更新变动 set 的 patternCount（= len(patterns)）
6) dry-run 输出：映射表 + 各表受影响行数 + 异常列表
```

**不变式（每次保存前全量校验）**

1. 每个 set 的 `patternCount` == 实际 pid 数
2. 同组 pid 连续，无空洞、无重复
3. 每个 pid 至少 1 条 flag 行，且恰好 1 条 playarea 行
4. 同一 set 内所有 flag 行的 `targetBoss` / `rareMap` 一致
5. flag 行的 `(eventFlag, modifier, modifierSet)` 能在 `LotBaseMapPatternFlag` 找到（或命中白名单：`7535/99999` 哨兵、`0x3E5…` 脏数据）
6. spot 行的 `attachId` 在 `SmallBaseAndSpotAttachPoint` 存在、`smallBaseMapId` 在 `SmallBaseMapVariationParam` 存在
7. 同一 pid 内同一 `smallBaseMapId` 的 `mapIndex` 从 0 连续累加
8. `variationId` 落在该 tile 真实存在的档位上（不存在的给黄灯，不拦）
9. `patternId` 未被两张表以外的任何表引用（已扫 252 张 paramdef：只有 flag / playarea / spots 三张）

**举例**：把 `set 35`（0 组，pid 155..159）从 5 个改成 6 个 → 0 组里 set 40..75 的 pid `160..319` 全体 +1（共 160 个 pid 平移）；1000 组完全不动。

## 六、保存管线与安全

### 6.1 管线（沿用现在这套，只是改成"保存"而不是"写回"）

```
内存模型 → 全量校验 → dry-run 摘要（人工确认）
        → 复制 params 到 work\write\<名字>_<时间戳>\
        → 在副本上做字段级 patch + 增删行
        → regtool pack
        → regtool unpack 对账（行数、目标行内容、未触碰表逐字节一致）
        → 备份原 bin（.prev_<时间戳>）
        → 覆盖
```

### 6.2 为什么要"字段级 patch"

现在写回只能追加行；新需求要改**已有行**（改 weight、改 patternId、删行）。做法：
在 param 表字节层按 `(表, 行 id, 字段偏移)` 定点写，避免整表重排。删除行 = 重写整表（行数变了），但只对受影响的表做。

### 6.3 备份与操作历史

- **会话级**：打开 bin 后第一次改动前存一份基线（`work\session\<hash>\base.params`），随时可"回滚到会话前"。
- **保存前**：原 bin 照旧 `.prev_<时间戳>`；`work\write\` 只保留最近 3 次，自动清旧的。
- **操作历史**：结构操作（A2–A5、A8）存全量快照；字段修改（A6/A9/A10）存差异。支持撤销/重做 + 历史列表（时间、操作、影响 pid 区间）。

## 九、风险与待验证

1. **分组结论是"拟合"出来的**：两份 bin 全对，但严格说这是数据拟合，不是引擎内部真相。
   建议验证：在 0 组中间某个 set 加一个 pattern，进游戏看 1000 组的种子是否完全不受影响。
2. **池子与实际不一致，游戏是否在乎**：现在的 `[Custom] 1096` 就是不一致的（池子 20、实际 1），文档记录它在游戏里跑通过（至少刷到过），但没专门验证过池子。
3. **`weight` vs `chaosMatchWeight`**：懂逻辑，工具只负责给两个输入框，不解释；但要确保写的是正确字段（+0 s32 / +14 s16，已按字节核对）。
4. **大众误操作**：删官方 set、改组合影响很大 → 二次确认 + 会话基线 + 保存前 dry-run。
5. **容量为 0 的 set**：官方存在，合法；但插入 pattern 前它没有 flag 行，夜王/地形只记在工具侧 + 名字里。

## 十一、Step 1 实测追加（2026-11-15，已实现 `app/core/patternset.py`）

Step 1 的产物：`app/core/patternset.py`（模型 + 规划 + 校验，**零写盘**）与 `tools/pset_report.py`（只读报表）。
在两份 bin 上跑通：`patternId = ⌊setId/1000⌋*1000 + 组内前缀和` **101/101 全一致**。

实现过程中修正了三处原先想当然的规则：

### 11.1 池子字段按「个数」处理（2026-11-15 决定）

- 一开始想按"权重"理解（因为 DLC 组写成 `1/1`），拍板：**当个数就好，不重要**。
- 所以现在的做法是**派生值**：
  - 新建 set → 池子全部清 0（空 set）；
  - 插入 pattern → 该 pid 的值 +1，自动写回 set 行；
  - 删除 pattern → -1（到 0 为止，槽位值保留、计数写 0）；
  - 另有 `plan_recompute_pools` 供手动对齐（官方 set 用）。
- 更新时**值留在原槽位，只改计数**（第一版按"合并重排"写，会把 210/180/601 互相搬家，看着像乱改，已修）。
- 自验：`set 0` 按实际重算 **0 处改动**（说明官方 base 组本来就自洽）；`[Custom] 1096` 重算出 **6 处**（化石数据）。


### 11.1b 组合 ↔ 地图类型旗标（实测）

`rareMap 0..5` 与 flag 行里那条「地图类型行」一一对应：

| rareMap | 0 普通 | 1 山顶 | 2 火山 | 3 腐败 | 4 Great Hollow | 5 隐城 |
|---|---|---|---|---|---|---|
| eventFlag | 7600 | 7601 | 7602 | 7603 | 7604 | 7605 |
| modifier | 10 | 11 | 12 | 13 | 14 | 15 |

所以改组合 / 跨组合克隆时，这几项要一起改：`targetBoss / rareMap` + 地图类型行的 `eventFlag / modifier`。
克隆时夜间 BOSS（`bossId1/2`、`bossModifier1/2`）从**目标组合**的参照 pattern 取（新 set 用官方同组合 set 的第一个 pid）。


### 11.2 mapIndex：官方索引唯一，但**不按文件顺序**

- 反例：pid 31 的 tile 4652 两行，文件里先出现 `attach 316 / mapIndex 1`，后出现 `attach 755 / mapIndex 0`。
- 所以「按文件顺序 0,1,2…」只适用于**我们自己新建的种子**；对官方 pid 必须**保留原值**。
- 新规则：
  - 克隆 pattern → 原样复制 mapIndex；
  - 新增一个地点 → 该 tile 取 `max(已有)+1`；
  - 校验 → 只查「同一 pid 同一 tile 的 mapIndex 是否重复」（官方 0 重复）。

### 11.3 空壳 tile 与空变体 tile 不报

- `2xxx`（2000–2199）14 个 tile 在 spot 表里被官方用了 33 次，但 `SmallBaseMapVariationParam` 里**没有行**（只有 define）。
- `4xxx` 里有 137 个 tile 有变体行但**所有 variation 字段都是 0**（如 4910），官方照样在 spot 行里填 `variationId=2`。
- 所以变体校验改成：只有该 tile **真有非 0 档位**时才检查 `variationId`。

### 11.4 顺带发现的化石 bug

现存 `[Custom] 1096`（pid 1200）的 44 行地点里，**同一 tile 的 mapIndex 全是 0**（例：tile 3410 出现 16 次，全 0）。
按 11.2 的"唯一性"规则这是**坏数据**，很可能就是当初那个"某处没 BGM"的化石（或手改出来的）。
建议：重构完成后把这个种子删掉重做，别再拿它当基准。

### 11.5 dry-run 的真实数据量（同一组内平移）

| 操作 | 平移 pid | 改 flag 行 | 改 playarea 行 | 改 spot 行 |
|---|---|---|---|---|
| set 35 插入 1 个（pid 155 克隆） | 160（0 组 160..319） | 1742 | 160 | 7210 |
| set 0 插入 1 个（pid 0 克隆） | 300（0 组 20..319） | 3288 | 300 | 13536 |
| 删除 pid 159 | 160 | 1742 | 160 | 7210 |
| 删除 set 1096 | 0（它在组内最后） | 0 | 0 | 0 |
| 改 set 1096 的 weight/chaosW | 0 | 0 | 0 | 0 |
| 改 set 35 组合 → 火山 | 0 | 56 | 0 | 0 |

结论：改中间 set 的容量，代价是"同组内几千行 patternId 改写"，但组与组隔离，不会波及另一组。

### 12.3 踩到的坑

- **"删除后 pid 不存在"不能当断言**：删掉 pid 20 后，后面的种子整体前移，20 号马上被旧的 21 号占用。
  正确的校验是"**被删那批行记录**不再存在"（按 `_id` 查），不是"这个号不存在"。
- 池子更新第一版会**把值在槽位里搬家**，已改成"值不动、只改计数"。
- 每步新建一份完整副本太费空间（57MB/份），改成 Session：基线 + 工作副本 + 快照（最多 8 份）。

### 14.6 圆圈与点击（2026-11-15 提的第一处 bug）

**问题**：一个点位上同时有小圈（建筑位）和大圈（地点），看着乱。

**改成**：
- 圆圈全部由前端画（服务端 PNG 现在只画图标和属性徽章，`render(..., rings=False)`）；
- 同一个位置两样都有 → **只画大圈，颜色用建筑位那个颜色**（大=蓝 / 小=绿 / 未知=灰）；
  匹配规则：优先按 `attachId` 认亲，认不到再按世界坐标（±14）；
- 没有地点占用的建筑位才画小圈；
- **点击判定 = 圆心距离最近**：点大圈 → 选中并高亮（粗白圈 + 外圈光晕 + 右侧地点表对应行变亮）；
  点小圈（空建筑位）→ 高亮 + 弹出建筑选择条。
- 顺手修的 bug：`spotView` 原来没带 `row`，导致"选中哪一行"对不上（还会让所有圈都显示成选中态）。

### 14.7 还是能看见小圈 → 孪生 attachId（2026-11-15 第二次反馈）

刷新后仍能看到小圈。查数据发现根因：
- **DLC 地形种子用的是 `21xx` 这一族 attachId**（例：pid 1105 的 44 个地点全在 2100/2101/2103…），
  而我们的建筑位池子是 `100/101/103…` → 按原号一个都匹配不上，于是 35 个建筑位全被当成"空闲"画出小圈。
- 验证：`21xx - 2000` 正好落回池子（`2100→100`、`2104→104`、`2190→190`…），
  命中数 35 个空闲 → **3~4 个**。

**改法**：认亲顺序 = 原号 → 孪生号（`±1000 / ±2000 / ±3000`）→ 世界坐标（±14）。
实测 pid 1105：小圈从 35 个降到 **3 个**（剩下的是真的没被这个种子用到）。

### 14.9 最终定稿的圆圈规则（2026-11-15 第三次确认）

> 原话：「小圈不用删，让大圈跟小圈走」——小圈是**校准过的建筑位**，位置才是准的。

| 图层 | 规则 |
|---|---|
| 小圈（建筑位） | **全部保留**，用校准坐标画，永远在最底层 |
| 大圈（地点） | 能认到建筑位（原号 / 孪生号 / 坐标）→ **圆心直接用建筑位坐标**；认不到 → 用原始坐标，颜色改白色 |
| 颜色 | 大圈颜色 = 它所属建筑位的颜色（大=蓝 / 小=绿 / 未知=灰）；认不到建筑位的用白 |
| 点击 | 圆心距离最近；同圆心时优先大圈（有地点就选地点） |
| 选中 | 大圈：粗白圈 + 外圈光晕；小圈：白描边 + 白点；右侧地点表对应行高亮 |

实现要点：服务端 `_spot_payload()` 里也做了"贴到建筑位"（图标位置跟着走），
实测 pid 1105 的 `attach 2100/2101/2104/2116` 与建筑位 `100/101/104/116` 坐标差 **0**。
